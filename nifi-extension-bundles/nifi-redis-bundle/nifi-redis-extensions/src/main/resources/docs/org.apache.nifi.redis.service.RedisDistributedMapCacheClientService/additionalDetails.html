Atomic operations and permissions

Conditional insert and replace operations act on one key at a time. The get-and-insert and compare-and-set operations use EVAL with a single explicitly declared key, keeping the read, conditional write, and TTL update together on the server. WATCH, MULTI, and EXEC are not required. Scripts and values are binary safe. Existing keys, values, and raw-value revisions retain their format.

The Redis user needs permission for EVAL and the commands executed by these scripts (GET and SET), as well as commands used by the cache operations the flow calls (including EXISTS, DEL, MSET, and EXPIRE). Configure key permissions for the serialized cache keys. A server configured to prohibit scripting cannot use this atomic cache service.

TTL is applied when an entry is inserted or successfully replaced. A failed comparison or an insert against an existing key leaves the value and its expiration unchanged. A TTL of 0 secs creates entries without expiration.

Deployment considerations

Single-key atomicity applies at the endpoint executing the operation. Redis Active-Active replication does not provide a globally serialized compare-and-set across regions. Flows that require global coordination, such as duplicate detection or Wait/Notify, should use one authoritative database rather than independent writable Active-Active regions.

Bulk putAll retains its existing MSET behavior; it does not promise a transaction across multiple hash slots. Follow the database's multi-key command restrictions and use a common hash tag when a deployment requires keys in one slot.
